# Dead ends, rejected experiments, and questions evidence cannot yet answer

A failed implementation is not a proof that its entire idea is impossible.
Conversely, an untested hypothesis does not become promising merely because
the old benchmark has been lost. This register includes both development dead
ends and dead ends encountered while reconstructing the history.

Disposition is fixed to the reviewed source `2f623c660` and the retained
historical evidence. These are follow-up specifications, not runs performed
by this documentation review. The [early](07-performance-early.md) and
[late](08-performance-late.md) chapters provide detailed numbers and source
links; [Hindsight](09-hindsight-crosswalk.md) records memory-only qualifications.

## Which kind of work can answer which question?

- **Static:** history, callers, shape predicates, layout contracts, and preserved
  artifact metadata can establish reachability, provenance or a concrete defect.
- **Correctness run:** CPU/backend comparison, output equivalence, quality,
  lifetime or compatibility tests determine behavior for exercised inputs.
- **Benchmark:** matched, route-verified measurements determine cost and benefit
  for a defined workload. Timing does not establish mathematical correctness.
- **Recovery:** locate the original binary, log, source object or environment
  record. A new experiment cannot reconstruct a missing historical observation.
- **New mechanism:** implementation or hardware/stack changes are prerequisites;
  repeating the unchanged rejected experiment does not answer a new question.

## Dead ends in this reconstruction

| ID | Evidence gap or contradiction | Work that can resolve it | What remains impossible from current evidence |
| --- | --- | --- | --- |
| H01 | No stable same-model, same-shape, same-driver benchmark spans March through October | New paired historical builds on one stack can estimate code evolution; preserved old binaries/environment would improve fidelity | A credible cumulative speedup cannot be obtained by multiplying unrelated published gains or joining early 25 t/s with later 60 t/s. Old stack behavior cannot be recreated from commit dates alone. |
| H02 | Author, committer, observation, archive and master landing dates differ | Git topology and first-parent diffs identify retained order; original PR events/reflogs could improve landing precision | Git author date alone cannot prove when a rebased commit reached public master. Benchmarking cannot answer a Git-publication question. |
| H03 | Original logs or development hashes are missing from the reviewed tree | Artifact recovery, remote source objects, or exact binary hashes may restore provenance | No new timing run can recover what an unpreserved process measured. Do not silently replace memory-only evidence with a later run. |
| H04 | P1.8 report calls configured context ceilings per-slot capacity | Static historical context/server allocation resolves interpretation; a new sustained multi-request workload measures the actual product capability | Existing health-plus-one-token probes do not establish concurrent throughput or long-context quality. |
| H05 | Hindsight stores old recommendations, sign inversions and retracted regression claims | Cross-check source revisions, arithmetic and later records, as in [crosswalk](09-hindsight-crosswalk.md) | Semantic recall cannot certify a binary, prove source absence or manufacture missing raw data. |
| H06 | Archive copies and repeated summaries make one experiment look like many | FILES.tsv hashes, source paths and run IDs identify duplicate evidence; use primary campaign trees | Duplicate bytes are not independent replications. Thousands of archived files do not imply thousands of controlled A/B trials. |
| H07 | GRF product files contain global provenance failures even with zero invalid cells | Read both global validation and per-cell flags; compare binaries and requested commits. [Late chapter](08-performance-late.md) | Numeric confidence intervals do not rescue a comparison of the wrong binaries. |
| H08 | Early October fault counters were broken and kernel logs absent | Recover original kernel records if any survive; later monitored sessions answer later stability only | Static analysis or new benchmarks cannot prove the unrecorded early session fault-free. |
| H09 | No matching i915 run for the cited production off-placement MoE comparison | Controlled reboot A/B with pinned stack and explicit placement would measure it | Auto-placement regressions cannot be generalized to production placement. | H10 | AOCC/kernel/runtime/build/host-load changes overlap in archive labels | Recover matching runner/provenance, use rotated same-configuration arms and explicit boot identity | A directory named for a compiler is not a compiler-only experiment. | H11 | Source defects and missing upstream fixes found in chapters 2-4 were not executed | Static failure scenarios support targeted correctness tests; builds/runtime reproducers then determine affected deployments | This history task cannot certify master or quantify exploitability/performance impact from source inspection alone. |
| H12 | Reported backend-wide absence was sometimes a check of the wrong checkout or disabled path | Pin the tree and inspect implementation, dispatch, guards and generated instantiations; require path counters in tests | A symbol existing is not proof it runs; a benchmark command naming an option is not proof the backend honored it. |

## Most useful next evidence, in order

1. Close route-independent FA correctness gaps before promoting the October MKL
   shape hypothesis. This protects numerical behavior before chasing a speedup.
2. Establish model-output equivalence for scheduler async copies and nonzero
   execution of the relevant replay/optimized paths. Only then time them.
3. Account for lazy prefetch/speculation memory inside fit and measure with
   exclusive VRAM ownership; keep allocator-mechanism claims separate from the
   practical observation that more headroom avoids an abort.
4. If a longitudinal performance claim is needed, choose one dense and one MoE
   workload, fixed outputs/depths/placement and matched historical builds on a
   single booted stack. Report build failures as missing cells, not zero speed.
5. Reopen LUT/XMX/InnerQ only with a changed mechanism or new hardware evidence.
   Otherwise the existing failures already answer the unchanged proposal.

These follow-ups are recommendations derived from the evidence review. No
benchmark campaign, service change, stack change or implementation fix was
started as part of writing this register.
